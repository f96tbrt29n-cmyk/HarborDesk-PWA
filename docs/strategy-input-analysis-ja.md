## 制御された製品不具合の再現

最初の1ケースでは押下時に遷移が既に終わり、running配列が空だった。編集は成功したが、この仮説の検証成立とは扱わない。

次の1ケースでは、実際のCSS padding遷移を押下前に準備し、その進行をネイティブpointerdownのcaptureで再開して、アプリの押下ハンドラーとの重なりだけを制御した。テストページのscroll anchoringを無効化し、位置変化が補償で隠れないようにした。アプリのハンドラーや既存の判定・タイムアウトは変更せず、WebKit/WPEのネイティブマウス入力を使った。

14d4a81では、pointerdownが編集ボタンへ届いた時のtopは477px。押下中のpadding遷移で483pxへ6px移動した。同じノードは接続されたまま、pointerupとclickは別のDIVへ届いた。pointercancelなし、処理後preventDefault=false、編集フォーム数0のままで12秒の表示アサーションに失敗。押下後のノード交換や取消ではなく、既存の遷移による位置変化で入力先が変わったこのケースの原因は確認できた。

これは制御した入力の失敗モードであり、元のCIの初回失敗と同一原因であることは証明していない。実機のタッチ入力の再現とも区別する。

## 製品修正と検証

`workspace-tabs.js`で、攻略リスト内の主ポインタ押下時に既に進行しているtopbarのpadding遷移を一時停止する。クリック・取消・blur・クリックを伴わない解除の既存経路で再開し、次の押下へ所有権を移す時も古い停止を残さない。新しいcompact変更の保留、500msの解除保険、既存の取消判定は維持する。元から停止済みの遷移・装飾だけの遷移には介入しない。

診断機能のコードは14d4a81から変更していない。保存キー、艦娘・装備・資源・同期・保存編成・計算プランの形式、海域条件、所持数判定には変更がない。

同じ制御失敗ケースは修正後に成功。恒久回帰2ケース（クリック、取消後のキーボード編集）を各3回、Chromium/WebKitで計12件成功、再試行0。全12件で押下時と保持中の位置差0、同じノード、クリック/取消後の遷移再開を確認した。詳細は `strategy-active-header-transition-evidence.json`。

既存8操作と必須装備保持4ケースは両エンジン計24件成功、再試行0。既存ヘッダー2ケース・6保存キー・新規回帰の資料出力を通常のCI設定で各1回検証した工程は10件中9件成功・1件失敗。失敗はWebKitの既存マウスfixtureが、native pointerdownより前の座標ヒット確認でfalseになったもの。新しい停止処理を試す段階に到達しておらず、押下中の不具合と区別する。ただし準備状態が不成立だった原因は未確認で、製品のスクロール処理起因も排除しない。

失敗時の画面はホーム先頭を表示していたが、ヒット確認時の矩形・scrollYは記録がなく復元できない。判定を維持した単独の計測1ケースでは成功し、scrollY=3948、ボタンtop=698、入力点はボタンに当たり、headerPress=falseだった。この成功を当該fixtureの安定成功と扱わない。追加する場合は、既存の座標確認と同じ評価内で矩形・ヒット要素・scrollYを保存し、失敗後に添付する最小限の計測で十分。無目的の成功反復で原因を決めない。

6保存キーは両エンジンで文字列一致を確認。Node4検証ファイル、変更したJS構文、差分チェックは成功。製品修正は未公開で、元のSafari/WebKit初回失敗の根本原因は引き続き未確認。
