# 手持ち配備・先制対潜の確認手順

先制対潜の発動条件は `fleet-readiness-evaluator.js`、装備・人数・所持個体・海域条件の統合は `owned-equipment-planner.js` で評価します。装備性能は既存の公式マスター参照を使い、未登録値は推測で補完しません。

## 計算の根拠と範囲

- [攻略Wikiの先制対潜条件](https://wikiwiki.jp/kancolle/対潜攻撃#trigger_conditions)、[KC3Kai Ship.canDoOASW / equipmentChangedEffects](https://github.com/KC3Kai/KC3Kai/blob/master/src/library/objects/Ship.js) を参照（2026-10-13確認）。同期の `api_taisen[0]` は装備込みの表示値です。
- 同じ装備・改修値の組み合わせには同期値を使用。装備なしで同期した値がある場合は「素対潜＋装備素対潜」を下限として使用し、未知の艦固有ボーナスを加算しません。下限が閾値未満なら未判定にします。
- 過去の装備なし同期値は、改造段階・Lv・同期された近代化改修配列が一致する場合だけ保持します。Lv・改造・改修データが変われば破棄します。手入力の表示値は、個体・装備・同期情報が変われば再確認します。
- 次期ビルドでは、マスターの装備枠数と一致する完全なスロットID配列がある場合だけ基礎対潜値を記録します。空配列・枠不足・不明なIDは装備なしの証拠にしません。不完全なスロット情報では以前の装備情報を消さず、未確認として扱います。枠数の根拠がない旧基礎値は保存データを削除せず未判定にし、同じ装備の同期表示値は引き続き使用します。装備を変更する場合は通常の同期で根拠を更新してください。
- ゲーム艦隊と連動する保存編成でも、欠損同期時は以前の装備・搭載位置・個体IDを保持します。過去の装備記録でゲーム反映済みとは判定しません。完全な同期で実際に装備が空になった場合は、正常に空の装備へ更新します。
- 7-1の初期配備目標は[攻略資料](https://zekamashi.net/kancolle-kouryaku/7-1/)にある4〜5隻の下限4隻。他海域の人数推奨が未登録なら対潜対策海域は初期1隻です。人数は攻略の配備目標で、ルート固定条件ではありません。ルート・戦闘・基地支援に応じて利用者が変更してください。
- 全登録海域について登録済みの艦種・隻数・旗艦・速力・索敵・制空・特殊装備・基地条件を統合します。ただし全ルートの条件網羅は未完了です。「登録範囲の条件を充足」は攻略成功の保証ではありません。不明なルート・索敵閾値・敵編成・装備性能は未判定です。
- 先制対潜が可能になる厳密な必要Lv、全艦・全装備のボーナス差分は未対応。同期Lvと海域の推奨Lv帯との差を表示します。
- 代替探索は所持個体を使い、入渠・遠征・同期大破状態を除外。推奨Lv帯に近い艦を優先し、重複・登録ルート条件と装備条件を再評価します。候補数・装備組合せ数に上限があり、解の存在を保証しません。

## iPhone Safari

1. 対象ビルドを開き、アプリ情報でビルド番号を確認します。同期HPを定期取得する設定は追加していません。
2. ゲーム連携で司令部Lv・艦娘・装備を取り込みます。艦隊台帳で個体ID、Lv、表示対潜値を確認します。装備なし同期の下限を使いたい艦はゲーム側で装備を外してから通常の同期を1回実行します。
3. 海域の自分用編成を選び、編成例と「先制対潜艦の配備目標」を設定します。1-5なら選んだ攻略方針に合わせ、対潜艦を揃えます。探索後、各艦のソナーなどが同じ艦に配備され、同じ装備の使用数が所持数を超えないことを確認します。
4. 対潜値が1足りない状態、ソナーなし、別改造段階、未登録装備、同じ艦を2枠に指定した状態を試します。不足／未判定の表示と入手・改修候補を確認します。台帳が空なら所持を成立扱いにしません。
5. 未判定の艦には、提案と同じ装備をゲーム側で実際に配備して同期するか、その装備での表示対潜値を入力します。実測値99/100などの境界で判定が切り替わることを確認します。
6. 「所持艦娘・代替装備で再探索」を実行します。変更された艦名・個体・Lv、残る不足を確認します。解がない場合の表示も確認します。
7. プランナーへ移動し、司令部Lvが同期値、艦娘・装備・改修値・スロット位置が提案と一致することを確認します。
8. 保存編成に反映し、再読み込み後に艦名・個体ID・配備目標・装備が保持されることを確認します。別編成や資源・台帳が変わらないことを確認します。
9. 台帳・装備・人数目標を変更した後、古い探索案で保存・プランナー上書きができず、再探索が必要になることを確認します。

## ホーム画面PWA

1. Safariの共有からホーム画面に追加して起動し、同じ手順3〜9を実行します。Safariとホーム画面では保存領域が異なることがあるため、各画面で同期情報を確認します。
2. オンラインで一度起動してキャッシュを作り、ホーム画面アプリを終了。機内モードで再起動して画面・同期済み台帳・保存編成・プランナーが表示されることを確認します。
3. オンラインへ戻し、新ビルドへの更新後も保存データが保持されることを確認します。横にはみ出す入力欄・ボタンや、タップできない候補がないことを確認します。

## 自動検証

`npx playwright test tests/owned-oasw-integration.spec.js --project=chromium` と同じコマンドの `--project=webkit` を実行します。追加テストは既存の `npm run test:browser` にも含めています。Service Workerを有効にしたキャッシュ・再読み込み（Chromiumではオフライン再読み込み）、同期値・人数・所持数・代替案・保存・再読み込み・プランナー連携を検証します。デスクトップWebKitはiPhone実機のホーム画面動作そのものを証明しないため、上の実機手順を併用してください。

Playwright WebKitの `setOffline(true)` 後の再読み込みは、Service Worker制御下でもエンジン内部エラーになるため、自動テストではキャッシュの存在とオンライン再起動を確認します。WebKitのオフライン起動はiPhone実機手順で確認してください。
