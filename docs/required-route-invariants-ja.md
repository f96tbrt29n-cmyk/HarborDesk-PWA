# 自動編成・手持ち配備の必須条件保護

基準mainは `f6fbe2f4c7144a6db4a6dad2a92c2573e132c771`（公開版v1.0.577）。作業は別worktreeの `codex/required-route-invariants`。PR #151の調査ブランチ・未保存データには変更しない。公開版の版・build・キャッシュも変更しない。

## 確認した原因と修正

- 経路全体の成立状況しか保護しないため、一部条件が不足した編成では、成立済みの史実艦などを失っても同じ「不足」になり、交換を拒否できなかった。登録条件を個別に評価し、各成立済み条件を装備探索・最適化・代替艦探索の交換前後で保護する。ANDは個別条件、ORは代替成立を許す一つの条件として扱う。
- 最適化切替・比較・保存で簡易編成を再生成し、直前の配備を失う経路があった。実際のキャッシュ配備を複製して次の最適化の基準とする。共通判定が未読込の間は交換を実行しない。「標準配備に戻す」も成立済み条件を破壊する場合は元の配備を保持する。
- 最適化の保存で個体ID・選択経路・空きスロットの位置を失った。これらを保持し、新しい評価を保存する。再読込では記録された評価を信用せず、実際の装備から再計算する。
- 空き枠を含む装備文字列の区切りが、再読込で装備名 `/` に化けた。隣接する空きスロットと増設位置を保つ解析に修正した。保存データの一括書換え・初期化は行わない。
- 代替艦探索が残りの艦の装備まで空にした。元の配置を引き継ぎ、交換艦への装備可否・所持個数と成立済み条件を再検証する。
- 未登録の艦娘・装備を解析できない配備案が元の保存編成を空欄で上書きする経路を保護した。未知の元データがある場合は自動保存を拒否し、元の文字列を保持する。
- 保存・プランナー反映でキャッシュの評価を利用した。現在の配備から必須条件と所持個体を再評価し、同期・台帳・司令部Lv・経路が変更された古い提案は反映しない。
- 艦の選択では史実艦・旗艦条件を優先し、同期個体の重複を除く。検証済み分岐グラフでは編成例の艦種構成を絶対条件とせず、実際の分岐条件で所持艦を再選択する。未確認の説明や不完全な再選択には適用しない。

経路必須・明示した戦闘方針・海域推奨を区別する。必須条件を新たに成立させる交換では推奨装備の不足を許すが、明示した方針や成立済み必須条件は失わない。1-2の「高速統一 OR 軽巡1＋駆逐4」のように、別の確認済み条件で速力制約が不要になった場合は、元の各艦高速化目標の消滅を不成立と誤判定しない。

## 表示と残る限界

個別必須条件に「成立」「不成立」「未確認」を表示する。不足値・装備艦数、艦種・所持個体、配備可能枠、既存の装備候補・入手方法、先制対潜の艦別不足表示を引き継ぐ。実際の最終経路が成立しなければ探索完了と判定しない。「登録範囲の条件を充足」と戦闘勝利保証は区別する。

探索は有限幅・候補数上限のある探索であり、手持ちで成立する全組合せを必ず発見する完全探索ではない。成立を証明できないときは不足・未確認を残す。任意手動編集を禁止するものではなく、編集後の現在値を再判定する。

## 検証記録

全て専用のローカルfixtureで実施し、利用者の保存データを操作しない。判定条件・タイムアウトは緩めず、Chromium/WebKitの再試行は0。

最初のmain上の再現では個別条件保護と保存経路の2件が失敗した。修正途中の検証では空き枠解析の製品不具合と、新規対空fixtureの艦種・装備不適合を区別して修正した。関連回帰358件は356成功、数値探索fixture2件失敗。このfixtureは検証済みグラフ指定なのにグラフ条件がなかったため、数値目標を維持して専用2隻条件を明示した。製品の攻略条件は変更しない。

追加の分岐回帰190件では184成功、編成再選択の3種類が両エンジンで失敗。未完成の再選択を採用しないこと、評価する艦種の保持、別の確認済み分岐で不要となる速力目標の扱いを修正する。この3種類と数値fixture、既存の編成例生成の再検証10件は全件成功（Chromium5・WebKit5、再試行0）。

Node・構文・マスター検証を実施。保存・再読込・プランナー、同期変更による古い提案の拒否、主要6キーの保持、5つの最適化切替、代替艦・装備、先制対潜、制空・索敵・装備保持を検証する。中間失敗は安定成功として数えない。
